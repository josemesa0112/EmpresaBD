# **Respuestas a las Preguntas Teóricas Complementarias**

## **1\. Diferencias e incompatibilidades entre SQL Server 2000/2005 y SQL Server 2022**

Cuando se realiza una migración desde versiones antiguas como SQL Server 2000 o 2005 hacia SQL Server 2022, es necesario revisar varios aspectos, ya que algunas características utilizadas anteriormente pueden no funcionar o haber quedado obsoletas.

* **Tipos de datos:** algunos tipos como `TEXT`, `NTEXT` e `IMAGE` están deprecados desde versiones anteriores y se recomienda reemplazarlos por `VARCHAR(MAX)`, `NVARCHAR(MAX)` y `VARBINARY(MAX)`, respectivamente. Tipos como `SMALLDATETIME` y `DATETIME` todavía existen, pero actualmente se recomienda utilizar alternativas como `DATE`, `TIME`, `DATETIME2` y `DATETIMEOFFSET`, debido a que ofrecen mayor precisión y un rango de fechas más amplio. Por ejemplo, `DATETIME` tiene como límite inferior el año 1753\.  
* **Funciones y sintaxis antiguas:** algunas formas de escribir consultas que eran válidas en versiones antiguas ya no son compatibles. Un ejemplo es el uso de `*=` y `=*` para realizar joins externos, ya que esta sintaxis fue eliminada y debe reemplazarse por `LEFT JOIN` o `RIGHT JOIN`. También existen procedimientos y funciones antiguas, como `sp_addlogin` y algunas funciones relacionadas con fechas, que ya no se recomiendan o fueron reemplazadas. Además, es importante revisar el uso de `RAISERROR` con la sintaxis antigua y considerar `THROW` como alternativa más moderna.  
* **Seguridad:** la seguridad de SQL Server ha evolucionado bastante con el tiempo. SQL Server 2022 utiliza protocolos de cifrado más actuales y ya no admite algunos métodos de autenticación o algoritmos considerados débiles. Los logins que utilizan mecanismos de almacenamiento de contraseñas demasiado antiguos pueden requerir que sus credenciales sean regeneradas. También ha cambiado la forma de administrar permisos, dando mayor importancia al uso de esquemas (`SCHEMA`) frente al modelo de propietarios de objetos que era más común en SQL Server 2000\.  
* **Nivel de compatibilidad de la base de datos:** una base de datos creada en una versión antigua no siempre puede pasar directamente a SQL Server 2022\. Dependiendo de su versión y nivel de compatibilidad, puede ser necesario realizar primero una migración intermedia. Por ejemplo, una base de datos muy antigua podría tener que pasar primero por SQL Server 2008 R2 o SQL Server 2012 antes de llegar a SQL Server 2022\.  
* **T-SQL y comportamiento del sistema:** algunos procedimientos escritos hace muchos años pueden depender de conversiones de tipos implícitas o de determinados comportamientos del motor antiguo. Estos comportamientos pueden cambiar al utilizar las versiones modernas y su optimizador de consultas. También existen configuraciones que han cambiado con el tiempo, como el comportamiento de `NULL` al concatenar cadenas mediante `CONCAT_NULL_YIELDS_NULL`.

Por estas razones, una migración no consiste simplemente en copiar la base de datos de una versión a otra. Es necesario revisar el código y comprobar que las características utilizadas anteriormente sigan siendo compatibles.

## **2\. Pasos para migrar procedimientos almacenados sin perder funcionalidad**

Para migrar los procedimientos almacenados correctamente es recomendable hacerlo de manera organizada y realizar diferentes pruebas antes de llevar los cambios a producción.

1. **Realizar un inventario y análisis:** primero se deben identificar todos los procedimientos almacenados, funciones y triggers existentes. También es importante documentar para qué sirve cada uno, qué parámetros recibe y de qué otros objetos depende, como tablas, vistas o procedimientos almacenados adicionales.  
2. **Extraer el código fuente:** después se debe obtener el código de cada procedimiento almacenado. Esto se puede hacer mediante SQL Server Management Studio (SSMS), utilizando la opción de generar scripts, o mediante consultas a `sys.sql_modules`. De esta manera se conserva el código T-SQL original y se puede trabajar con él fuera de la base de datos antigua.  
3. **Revisar la compatibilidad:** cada script debe revisarse para encontrar elementos que ya no sean compatibles con SQL Server 2022\. Esto incluye tipos de datos obsoletos, sintaxis antigua para joins y funciones que hayan sido eliminadas o reemplazadas. Una herramienta útil para esta tarea es **Data Migration Assistant (DMA)** de Microsoft, que permite identificar varios de estos problemas automáticamente.  
4. **Realizar la migración en un entorno de pruebas:** antes de modificar la base de datos de producción, se debe crear un entorno de prueba o *staging* en SQL Server 2022\. Allí se ejecutan los scripts corregidos y se comprueba que los procedimientos funcionen correctamente.  
5. **Realizar pruebas funcionales:** cada procedimiento debe ejecutarse utilizando datos de prueba que representen situaciones reales. También es importante probar casos especiales, como valores `NULL`, cadenas vacías y fechas extremas. Los resultados obtenidos en SQL Server 2022 deben compararse con los resultados generados en el sistema antiguo.  
6. **Revisar el rendimiento y los planes de ejecución:** el optimizador de consultas ha cambiado considerablemente entre las versiones antiguas y las actuales. Por eso, un procedimiento que antes funcionaba rápidamente podría presentar un rendimiento diferente después de la migración. Se deben revisar aspectos como índices faltantes, búsquedas mediante índices y posibles escaneos completos de tablas.  
7. **Realizar una migración incremental y utilizar control de versiones:** es mejor realizar los cambios por grupos o módulos funcionales en lugar de modificar todo al mismo tiempo. Además, mantener los scripts en un sistema de control de versiones como Git permite saber qué cambios se hicieron, rastrear errores y regresar a una versión anterior si es necesario.  
8. **Realizar el corte y la validación final:** cuando todo haya sido probado en el entorno de staging, se puede realizar la migración a producción durante una ventana de mantenimiento. Después del cambio se deben ejecutar pruebas rápidas o *smoke tests* para confirmar que los procesos principales continúan funcionando correctamente.

En resumen, la migración debe hacerse de forma controlada, realizando pruebas tanto de funcionamiento como de rendimiento para evitar que los procedimientos pierdan alguna de sus funciones originales.

## **3\. Estrategia para validar que los datos migrados son consistentes con el origen**

Después de realizar la migración, no basta con comprobar que las tablas existan en el nuevo servidor. También es necesario verificar que los datos se hayan trasladado correctamente y que no se hayan perdido, duplicado o alterado durante el proceso.

* **Comparar el número de registros por tabla:** una de las primeras comprobaciones consiste en comparar la cantidad de filas de cada tabla en la base de datos original y en la nueva. Si los números no coinciden, puede indicar que se perdieron registros o que algunos fueron duplicados durante la migración.  
* **Utilizar checksums o hashes de control:** también se pueden calcular valores de control utilizando herramientas como `CHECKSUM_AGG` o `HASHBYTES` sobre determinadas columnas. Estos valores se calculan tanto en el origen como en el destino y luego se comparan. De esta manera se pueden detectar diferencias en el contenido que no serían evidentes simplemente comparando el número de registros.  
* **Comprobar la integridad referencial:** es necesario verificar que las llaves foráneas continúan apuntando a registros que realmente existan en las tablas relacionadas. También se deben revisar las restricciones `CHECK` y `UNIQUE`, para asegurarse de que los datos que estaban presentes en el sistema original no hayan sido rechazados o afectados por las restricciones del nuevo esquema.  
* **Realizar un muestreo dirigido:** se puede seleccionar una muestra de registros importantes y compararlos campo por campo entre el sistema original y el nuevo. Por ejemplo, se podrían revisar pedidos de mayor valor o clientes que tengan una gran cantidad de transacciones. Se debe prestar especial atención a fechas, números decimales y textos que contengan caracteres especiales como tildes o la letra `ñ`, ya que estos datos pueden presentar problemas durante una migración.  
* **Realizar pruebas de reconciliación mediante datos agregados:** además de comparar registros individuales, es útil comparar algunos valores generales del negocio. Por ejemplo, se puede calcular la suma total de los pedidos o el stock total de productos en ambos sistemas. Si estos valores son diferentes, puede existir algún error en los datos migrados que no se haya detectado mediante las comprobaciones anteriores.  
* **Realizar pruebas funcionales de extremo a extremo:** finalmente, se deben ejecutar procesos normales del sistema utilizando los datos migrados. Por ejemplo, crear un pedido, consultar información o generar un reporte consolidado. El objetivo es comprobar que los datos no solo estén presentes, sino que también permitan que los procesos de negocio funcionen de la misma manera que antes de la migración.

De esta forma, se puede tener mayor seguridad de que la migración mantuvo tanto la información como la funcionalidad del sistema original.
